## Why

`reactor:v1.0.1` failed Maven Central's component validation today (missing dependency version for `io.projectreactor:reactor-core`) while the other 8 modules of the same release, published independently via `io.github.sgtsilvio.gradle.maven-central-publishing`, may already have gone live — a partial release. That plugin uploads each module as its own Central Portal deployment, so one module's defect can't block the rest. Moving to `com.gradleup.nmcp.settings` aggregates every module's publication into a single Central Portal deployment, making the release atomic: one bad POM blocks everything, nothing partially leaks. The specific dependency-version defect itself is fixed separately and architecturally: `reactor-core` moves to `compileOnly` (it's a peer dependency every consumer already brings for their own Flux/Mono code) so it's never part of `reactor`'s published dependency list at all, and the internal `:dependencies` version-management platform is kept off every published module's `implementation`/`api` scope so it can never leak an unresolvable `dependencyManagement` import again.

## What Changes

- **BREAKING**: Remove `io.github.sgtsilvio.gradle.maven-central-publishing` from every publishable module (`annotations`, `processor`, `spi`, `strategies-builtin`, `reactor`, `reactor-blocking`, `percolate`, `bom`, `lib:javapoet`) and from `settings.gradle`'s `pluginManagement`/root `build.gradle`'s `apply false` declaration. Each module declares plain `maven-publish` instead (this plugin never applied `maven-publish` transitively; nmcp doesn't either, so modules must now apply it directly).
- Add `com.gradleup.nmcp.settings` (v1.6.1) in `settings.gradle`, configured via `nmcpSettings { centralPortal { ... } }` with `publishingType = AUTOMATIC` (same hands-off release behavior as today, just atomic across all modules) and the existing `mavenCentralUsername`/`mavenCentralPassword` property names (no GitHub secrets renaming).
- Keep `io.github.sgtsilvio.gradle.metadata` exactly as-is (license/developers/GitHub URL/SCM); its cascade trigger moves from the old plugin id to `maven-publish`.
- `buildSrc/percolate.conventions.gradle`: restructure the `withPlugin` reactive wiring so `signing` and `io.github.sgtsilvio.gradle.metadata` both cascade from `maven-publish` (the new anchor plugin every module declares) instead of the removed plugin id. The existing sources/javadoc jar and publications wiring is unchanged.
- Update the `signing { required { ... } }` gate: the string match on task name (currently `contains('MavenCentral')`) must match nmcp's actual task name instead.
- `.github/workflows/release.yml`: replace `./gradlew generateMetadataFileForMavenPublication` + `./gradlew publishToMavenCentral` with `./gradlew publishAggregationToCentralPortal`, run once at the root (not per module). GPG import step and `mavenCentralUsername`/`mavenCentralPassword` env vars are unchanged.
- `reactor/build.gradle` and `reactor-blocking/build.gradle`: move `io.projectreactor:reactor-core` from `implementation` to `compileOnly` — it's a peer dependency (any consumer of these modules already writes Flux/Mono mapper code and so already depends on `reactor-core` themselves), so these modules must not redistribute or pin a runtime version of their own. This removes `reactor-core` from the published POM's dependency list entirely, rather than merely fixing its version.
- Considered and rejected: `io.freefair.maven-central.validate-poms`, wired into `check`, as a POM pre-flight gate. Decompiling the plugin's `ValidateMavenPom` task showed it only checks POM *metadata* completeness (groupId/artifactId/version/name/description/url/licenses/developers/scm) — it does not inspect dependency entries at all, and would not have caught today's actual bug. Dropped from scope rather than kept for a benefit it doesn't provide.

## Capabilities

### Modified Capabilities
- `maven-central-publishing`: publish mechanism changes from per-module independent Central Portal deployments (`io.github.sgtsilvio.gradle.maven-central-publishing`) to one aggregated, atomic deployment (`com.gradleup.nmcp.settings`); the "declare only the primary publishing plugin" requirement inverts (modules now declare `maven-publish` directly, with metadata/signing cascaded from it).

## Impact

- **Build config**: `settings.gradle`, root `build.gradle`, `buildSrc/src/main/groovy/percolate.conventions.gradle`, `buildSrc/build.gradle`, and all 9 publishable modules' `build.gradle` files (plus `reactor`/`reactor-blocking`'s dependency scoping for `reactor-core`).
- **CI**: `.github/workflows/release.yml` publish job (task name and invocation scope change from per-module to root-level aggregated).
- **Release safety**: eliminates the partial-release failure mode observed with `reactor:v1.0.1` today; trades it for an all-or-nothing release (a single module's defect now blocks the entire release rather than leaking the rest). Today's specific defect class (missing dependency version) is separately closed off architecturally, not by an added validation gate.
- **Consumer-facing change**: projects consuming `io.github.joke.percolate:reactor` or `:reactor-blocking` must now declare their own `io.projectreactor:reactor-core` dependency (previously pulled in transitively) — expected to already be the case for any project using Flux/Mono mapper support, but worth calling out since it's a behavior change for existing consumers. No other published artifact coordinates, POM content requirements, or signing guarantees change.
